# Eval 简明设计

> 本文只说明 Eval 的目标、流程和关键设计。已保存的具体结果、指标解释和典型轨迹见[结果索引](../results/README.md)；新运行产物写入 `outputs/evaluation/`。

## 1. Eval 要解决什么

Eval 使用同一任务集比较 Base、SFT 和后续 RL，回答四个问题：

1. 轨迹是否有效，工具和环境是否正常工作；
2. 模型是否购买，以及最终商品是否满足用户需求；
3. 搜索、候选利用、证据核验、购买决策和终止过程是否合理；
4. 失败来自模型，还是任务、环境、Harness、验证器或 Judge。

结果和过程分开报告，不合成一个难以解释的总分。

## 2. 总体流程

1. **冻结任务和 Rubric**：根据用户原始需求，把每个任务拆成独立的硬性要求和软性偏好；所有模型共用同一版本。
2. **运行 Agent**：Harness 让模型与 ShopSimulator 交互，保存完整轨迹和最终环境状态。
3. **Rule Gate 预检查**：程序检查格式、Action Guard、非法动作、循环、截断、预算耗尽、环境异常和明确的终局事实。
4. **Rubric 需求判断**：经过校准的 LLM Judge 根据用户需求、冻结 Rubric 和模型可见轨迹，逐条判断要求是否满足。
5. **过程评测**：Judge 根据用户需求、冻结 Rubric 和模型可见轨迹，对五项过程能力分别打 0–2 分。
6. **冲突与人工复核**：环境结果与 Judge 冲突、Gold 与 Rubric 冲突、证据不足或低置信度时进入人工复核。
7. **汇总与成对比较**：生成单模型报告，并按相同 `task_id` 比较 Base、SFT 和 RL。

已有轨迹可以反复离线评测。只要轨迹保存了新指标需要的信息，修改评测方法后不需要重新运行模型。

## 3. 程序和 LLM 怎么分工

当前不再设置“确定性 Rubric”。程序和 LLM 按评价对象分工，而不是共同判断同一条 Rubric。

| 层次 | 负责内容 |
|---|---|
| 程序 Rule Gate | 工具 Schema、动作是否合法、Guard 拒绝、循环、终止、上下文、环境/服务异常和行为次数 |
| 环境结果验证器 | 是否购买、实际 ASIN、实际价格和选项、是否命中环境参考目标或有效替代 |
| LLM Rubric Judge | 用户提出的每条硬性要求和软性偏好是否满足，包括价格、数量、规格、同义表达、颜色类别、功能、风格和用途适配 |
| LLM Process Judge | 搜索策略、候选利用、证据核验、购买决策和终止效率 |
| 人工复核 | 环境结果与 Rubric 冲突、Gold 与硬性要求冲突、低置信度或证据矛盾 |

轨迹中确实保存了结构化价格和选项，但这只能证明“实际值是什么”。从用户自然语言中提取的要求究竟是严格上限、近似偏好还是语义类别，仍需要理解上下文。为了避免重复建设一套脆弱的自然语言规则，当前设计让 LLM 对所有 Query Rubric 统一判断；程序提取的客观事实可以作为 Judge 的证据，但不直接产生 Rubric 的 `satisfied / violated` 结论。

## 4. LLM Judge 看什么、输出什么

Judge 只看：

- 用户原始需求；
- 冻结 Rubric；
- 模型当时可见的页面内容；
- 搜索、点击、选项、购买和 Guard 拒绝等完整轨迹；
- Rule Gate 提取的公开事实和待判断 Rubric 项。

Judge 看不到 Reward、Gold ASIN、模型身份和 Actor 未见的隐藏商品事实。

对每条 Rubric，Judge 输出 `satisfied / violated / unknown / conflicting`、理由、证据事件 ID 和置信度，不输出一个 Rubric 总分。它另外对搜索策略、候选利用、证据核验、购买决策和终止效率分别打 0、1、2 分。

## 5. 最终报告

每个 Run 保存三类结果：

1. **终局结果**：是否购买、目标商品或有效替代、错误购买或未购买；
2. **需求结果**：硬性要求和软性偏好的满足、违反、未知和冲突；
3. **过程结果**：五项过程分数、行为统计和第一处关键失败。

所有比例同时报告分子和分母；非模型无效和人工复核样本单独列出。

## 6. Eval v2 与旧结果

旧 Eval 在原项目的 Rule Gate 与 LLM Judge 之间额外加入了确定性 Rubric 判断，导致“米色—浅色系”和“S—小码”等语义关系被严格字符串规则误报为 `violated`，并阻止 LLM 复核。

`eval-v2` 已移除确定性 Rubric 的最终判定权，由 `deepseek-v4-pro` 重新评价全部 1,428 条要求。24 条 Gold 轨迹中的 182 条 Rubric 已按同一口径完整复核：需求只评价最终购买商品；没有购买时不能把浏览过的候选算成满足。Gold v6 修正一处“硬要求未核验却标成无失败”的归因矛盾后，V4 Pro 已通过冻结门槛。正式评测使用已保存的 400 条轨迹，模型和环境都不需要重新运行。

旧评测结果保留用于追溯，但旧 Rubric 统计视为暂定结果，不用于 Reward。新结果写入单独的 `eval-v2` 目录，不覆盖旧文件。

## 7. 设计依据

- 原项目 Evaluation 设计采用代码硬检查、冻结 Rubric、盲评 Judge 和分面汇总；这里保留这套设计原则作为旧版评测基线。
- [《AI Agents in Depth》第 6 章](https://bojieli.github.io/ai-agent-book/book/chapter6/)：确定性底线先验证，开放质量按 Rubric 评判，低置信度进入人工复核。
- [WebArena](https://proceedings.iclr.cc/paper_files/paper/2024/hash/4410c0711e9154a7a2d26f9b3816d1ef-Abstract-Conference.html)：优先验证任务完成后的功能正确性，而不是匹配固定动作路径。
- [τ-bench](https://arxiv.org/abs/2406.12045)：通过最终环境状态与目标状态对比验证客观结果。
- [AgentRewardBench](https://arxiv.org/abs/2504.08942)：规则容易漏掉有效成功路径，LLM Judge 也会误判，因此需要专家标注校准和混合验证。
