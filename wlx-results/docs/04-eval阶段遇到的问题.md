# Eval 阶段遇到的问题

本文记录 WLX Eval 建设过程中遇到的流程、方法和决策问题。这里不记录路径、接口报错等程序小 Bug，而是记录那些会影响“评测在测什么”和“结论是否可信”的问题。

## 1. 一开始混淆了 Eval 和 Reward

**问题：** Eval 和 Reward 都在判断轨迹好坏，很容易把它们当成同一套东西，直接开始设计 RL 分数。

**最终处理：** 先完成 Eval，再设计 Reward。Eval 用于测量和诊断，可以包含多个指标、人工复核和 `unknown`；Reward 是训练信号，需要更稳定、更便宜，并最终形成模型可以优化的数值。两者可以共享可靠事实，例如是否购买正确、是否超预算，但不直接把完整 Eval 当作 Reward。

## 2. “买对商品”不能只理解为命中参考商品

**问题：** 环境为任务保存了参考商品，但参考商品可能包含用户没有要求的额外属性。如果只比较商品 ID，模型买到另一个同样满足需求的商品也会被判错。

**最终处理：** 验证时以用户实际提出的要求为准。买到参考商品记为目标商品购买成功（`gold_purchase`）；没有命中参考商品，但满足全部关键需求时，记为有效替代商品（`valid_alternative_purchase`）。参考商品额外拥有、但用户没有提出的属性，不能被加入验证条件。

## 3. 只看最终购买结果，无法解释模型学到了什么

**问题：** 两条轨迹可能都失败，但一条已经找到正确商品，只差最后购买；另一条从搜索开始就完全跑偏。只报告成功率会把它们当成同一种失败。

**最终处理：** 将评测分为结果和过程。结果判断是否买对；过程分别评价搜索策略、候选利用、证据核验、购买决策和终止效率。五项独立报告，不压成一个总分。

## 4. 确定性判断和语义判断必须分开

**问题：** 有些事实可以由程序准确判断，例如有没有购买、价格是否超预算；有些问题需要理解语义，例如搜索词是否合理、某个替代商品是否真正符合模糊需求。如果全部交给规则，规则会过于僵硬；全部交给 LLM，又会增加不稳定性。

**最终处理：** 程序负责轨迹格式、动作合法性、循环、终止、环境异常和实际购买状态等客观事实；用户自然语言 Rubric 的逐条满足情况统一交给经过校准的 LLM Judge。环境结果和 Rubric 结果分栏保留，发生冲突时进入人工复核，不能让任何一方自动覆盖另一方。

## 5. 必须明确“模型看过证据”的含义

**问题：** “模型核对了价格和规格”容易被理解为模型必须显式写出思考，也可能被误判为只要模型声称“已经核对”就算完成。

**最终处理：** “看过”被定义为：在购买或停止之前，相关信息真实出现在模型可见的环境观察中。被 Guard 拒绝的查看动作、空白页面和模型自己的口头声明都不能作为证据。Judge 判断的是证据是否对模型可见、是否覆盖关键要求，以及最终动作是否与证据一致，不猜测模型的内心状态。

## 6. 格式正确不等于动作可以执行

**问题：** Base 的格式正确率达到 98%，但大量轨迹仍以 `invalid_action` 结束。起初这个结果看起来互相矛盾。

**原因：** 格式检查只判断工具名、JSON 参数和 Schema 是否正确。模型可能正确调用一个工具，但该工具在当前页面不可用，例如页面没有描述入口却调用查看描述，或者当前页面不能搜索却调用搜索。

**当前处理：** 阅读结果时结合格式面板和终止原因，分别识别真正的格式错误，以及当前页面不可执行、被 Guard 拒绝的动作。现有汇总中的 `invalid_action` 仍是较宽泛的历史名称，主要指后者，不能直接解释成 JSON 格式错误；后续若把该指标用于 Reward，应先把这两个原因正式拆开。

## 7. 模型失败和非模型问题不能混在一起

**问题：** 环境、Harness、模型服务、任务数据或验证器也可能出错。如果把这些轨迹直接算作模型失败，会错误降低模型表现，并可能误导后续 Reward 设计。

**最终处理：** 正式评分前先做评测资格检查：模型自身搜索或操作失败的轨迹继续参与评测；明确的环境、服务或 Harness 故障标记为非模型无效；环境与验证器冲突、证据不足的轨迹进入人工复核。报告同时展示被排除数量和实际分母。

## 8. Rubric 不能照抄参考商品属性

**问题：** 用户需求通常是一段复合自然语言，其中既有硬性要求，也有“适合送礼”“质量较好”等模糊偏好。直接使用参考商品属性会悄悄增加用户没有说过的条件；完全使用规则又无法处理模糊语义。

**最终处理：** 每个任务先从用户原始需求生成 Rubric，将复合需求拆成独立要求，标记硬性要求和软性偏好，并注明使用确定性规则还是语义 Judge。生成结果经过人工检查后冻结；后续 Base、SFT 和 RL 必须使用同一版本，不能根据某个模型的表现临时改标准。

## 9. LLM Judge 不能未经校准就直接使用

**问题：** LLM 能输出分数，不代表分数稳定可信。它可能因为最终购买成功就倒推过程良好，也可能把“证据不足”错误理解为“不满足”。

**最终处理：** 从 Base/SFT 轨迹中分层抽取 24 条样本，建立人工确认的 Gold Set，用它校准 DeepSeek Judge 的五项过程分数、需求状态和失败归因。正式 Judge 只能看到用户需求、冻结 Rubric 和模型当时可见的轨迹，不能看到参考商品 ID、Reward、模型身份或最终隐藏答案。低置信度、证据引用错误和判断冲突的结果进入复核队列。

**限制：** 这 24 条 Gold 和 Judge Prompt 都参与过开发，因此校准结果只能说明当前链路基本可用，不能当作独立的 Judge 泛化精度。

## 10. `unknown` 不能当作需求不满足

**问题：** 商品页面没有展示某个属性时，我们只能说证据不足。如果把这种情况直接判为违反要求，会把环境没有提供信息误算成模型选错商品。

**最终处理：** 每条需求允许 `satisfied`、`violated`、`unknown` 和 `conflicting` 四种状态。只有存在明确反证时才使用 `violated`；信息缺失使用 `unknown`；环境事实互相冲突时使用 `conflicting` 并进入复核。

## 11. 当前 200 个任务不再是严格的最终测试集

**问题：** 这 200 个任务已经被用于分析 SFT、修订 Rubric、校准 Judge 和讨论后续 Reward。如果继续把它们称为完全未见的最终测试集，会产生评测泄漏。

**最终处理：** 将当前 200 个任务定义为开发评测集（`dev-eval`），用于比较 Base/SFT、诊断失败和设计 RL。Reward 和超参数确定后，还需要冻结一批未参与这些决策的新任务作为最终评测集（`final-eval`）。

## 12. 修改指标时不应重新运行模型

**问题：** 如果每次调整指标都重新采样模型，轨迹随机性会混入评测变化，也浪费模型和环境运行成本。

**最终处理：** Harness 保存每个任务的完整轨迹。只要新指标依赖的信息已经被保存，就可以直接离线重新评测，不需要再次运行 Base 或 SFT。只有轨迹缺少新指标所需信息时，才需要重新采样。

## 13. 报告不能只给英文键名和一个总成功率

**问题：** `candidate_utilization`、`decision_quality` 等程序字段便于代码处理，但不方便不了解实现的人阅读；单一成功率也会隐藏无效样本和失败结构。

**最终处理：** 人读报告统一显示“中文名称（英文程序字段）”，并同时给出分子、分母、非模型无效数量和复核数量。Base/SFT 使用相同任务做成对比较，分别报告成功转移、五项过程变化和主要失败类型。

## 14. Rubric 的程序判断和 LLM 判断边界划得过宽

**问题：** 当前 Rubric 生成结果把部分需要语义理解的要求标成了确定性验证。程序随后进行严格文本比较，并把结果直接冻结为满足或违反，不再允许 LLM 复核。因此出现了“米色不属于浅色系”“奢华咖不属于咖啡色”“米白色不属于白色系”“S 不等于小码”等明显误判。

**原因：** 原设计中的 Rule Gate 主要负责工具格式、动作合法性、循环、上下文和环境状态等客观事实；Rubric 的语义满足情况由 Judge 根据可见轨迹判断。WLX 实现额外加入了确定性 Rubric 判断，但没有先判断某条关系是否真的能够用规则可靠决定，把“语义不匹配”误当成了“明确反证”。

**重新核对：** ShopSimulator 轨迹虽然保存了结构化价格和选项，但没有一套能够覆盖全部用户表达的冻结语义契约。`99 ≤ 100` 在已确认“100 元以下是严格上限”后可以计算；`S=小码`、`米色=浅色系`等关系却依赖商品语境或类别知识。为少量简单项保留确定性 Rubric，会与环境 Goal 验证重复，同时引入新的分流和维护成本。WebArena、τ-bench 等基准的确定性验证依赖专门设计的程序化目标状态，并不等于使用通用规则理解自然语言 Rubric。

**新决策：** 回到原项目的分层方式：Rule Gate 只检查轨迹与环境的客观事实；环境验证器独立报告购买终局；全部 Query Rubric 由校准后的 LLM Judge 逐条判断；环境结果与 Rubric 冲突、Gold 与硬性要求冲突或低置信度结果进入人工复核。程序可以向 Judge 提供实际价格和所选选项等事实，但不直接输出 Rubric 的满足或违反。

**影响：** 现有 Rubric 的细分满足率和违反率包含确定性规则结果，在全部 1,428 条 Rubric 重新交给 Judge、Judge 重新校准并离线重评 400 条轨迹前，只能视为暂定结果，不能直接用于 Reward。轨迹已经保存，不需要重新运行 Base、SFT 或环境。

## 15. Eval v2：统一由 V4 Pro 判断全部需求

**问题：** 旧 Gold Set 是按“规则先判、LLM 只判剩余项”的流程制作的。24 条轨迹都经过确认，但只留下了 147 条需要 LLM 判断的需求标签；35 条当时被规则提前处理的需求没有进入人工标签。如果直接复用旧校准结果，会把旧方法的边界问题带进新版本。

**阶段处理：** 新方法命名为 `eval-v2`。Rule Gate 只检查格式、动作、循环、终止、环境异常和实际价格/选项等客观事实；`deepseek-v4-pro` 对每条轨迹的全部 Rubric 项统一判断。第一轮校准先使用已经确认的 147 条标签，并在报告中公开标签覆盖率和各类型数量。生产 Judge 必须与通过校准的模型和 Prompt 哈希完全一致，新产物写入单独目录，旧 01–03 文档和旧结果继续保留。

**后续修正：** 第一轮校准发现逐项覆盖不足会妨碍统一口径，随后在 Gold v5 中补齐了全部 182 条要求；详情见下一节。

## 16. 第一次 Eval v2 校准暴露了 Prompt 与 Gold 口径不一致

**问题：** V4 Pro 的 Rubric、责任和失败归因均通过门槛，但五项过程分只有 67.5% 的精确一致率。逐条检查发现，这不是单纯的模型能力问题：Judge 会把“看过但没有购买的候选”当作最终商品需求已满足，也会把“没有点击信息子页”误解为没有核验；与此同时，旧 Gold 的部分过程标签仍按旧边界给分。

**典型例子：** `base:6781` 没有购买，Judge 却根据候选商品把多条需求判为满足；`sft:19238` 的标题、选项和价格已经展示关键证据，Judge 却因为 Features 为空降低核验分；部分循环耗尽轨迹在旧 Gold 中仍得到 1 分购买决策，与 Eval v2 的“被动结束为 0 分”冲突。

**最终处理：** Judge Prompt 升级为 `wlx-eval-v2-judge-prompt-v2`，明确需求只评价最终实际购买商品、`available_options` 不等于已选择、可见结构化字段本身就是证据、直接命中强候选不强制比较，以及被动耗尽不能获得 1 分决策。Gold 升级为 v5，补齐原先缺失的 35 条标签，使 24 条轨迹的 182 条 Rubric 达到 100% 覆盖，并按统一边界修正 16 个过程分。旧校准结果保留，新 Prompt 必须重新运行 24 条校准。

第二轮校准的过程总一致率为 84.2%、Rubric 为 95.6%、责任归因为 91.7%，只有首要失败原因为 16/24，距离门槛差 1 条。复核发现 `sft:10864` 的 Gold 一边承认“数码屏幕未核验”，一边把首要失败写成 `none`，属于 Gold 内部矛盾。Gold v6 将其改为 `insufficient_verification`，没有降低任何门槛；复算后首要失败为 17/24（70.8%），四项门槛全部通过，校准状态冻结。

## 阶段性结论

这套 Eval 最终确认：格式本身不是 SFT 的主要学习内容。SFT 的主要提升来自候选利用、证据核验、购买决策和及时结束。后续 Reward 设计应优先关注规格选择、预算约束、购买前核验以及非法动作或循环后的恢复，而不是继续把主要权重放在工具调用格式上。
